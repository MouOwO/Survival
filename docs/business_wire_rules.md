# 业务回包与本地配置规则（第一版）

本规则覆盖自有后台与游戏 Lua 间的业务 HTTP，不把 Steam 地图下载、Dota 战斗同步或 Lua→Panorama 消息当成同一条链路。目标是先保持业务语义和可恢复性，再减少重复字段、静态文本与缺省值；字节预算用真实业务样本验证，不宣称存在统一的“游戏回包必须小于某值”行业标准。

## 字段、静态数据与缺省值

1. 名称、说明、图标、排序、固定奖励定义和默认额度进入随游戏发布的本地公开配置。回包以数字字段号、数字枚举 ID、账号动态数量、状态及必要版本身份为主。服务器仍决定资格、价格、发奖、权益有效期及最终余额。
2. 第一版固定注册 300 个字段、3412 个公开存档配置 ID、40 个每日额度模板及 3 个常见状态模板。字段、枚举和模板 ID 从 1 开始；只允许追加，不重排、删除或复用。需要移除的定义保留槽位。配置变化增加新模板，原模板默认值不改写。
3. 只省略协议模板明确声明的默认值。模板必须与原对象的完整 key 集合完全一致；模板内未变化的 false、0、null、固定文字均不发，由匹配版本的本地表恢复。未知字段、额外字段、false 与 0 的差异、null 与缺字段的差异全部保留。
4. 示例：无 VIP 的完整状态可以只含“无权益”模板 ID，不重复派发 `vip:0`、`vip1:false` 或静态名称。只有模板明确约定该语义时才能省略。不能用 `if not value` 一类递归过滤器清除整个业务 JSON 的零值。
5. 本协议压缩的是完整表示，解码结果应与原响应逐值、逐类型一致。它不是存档 patch：缺字段不表示“沿用本机旧值”。若以后引入增量，必须另有协议版本、账号/会话/基线 revision 校验、显式删除或清零操作和完整重读退路。VIP 到期、卸下装备、领取后熄灭提示尤其要检查旧值清除。

数字字段、默认值省略和字段存在性可参考 [Protobuf proto3](https://protobuf.dev/programming-guides/proto3/)、[字段存在性说明](https://protobuf.dev/programming-guides/field_presence/)及[兼容性建议](https://protobuf.dev/programming-guides/dos-donts/)。这些提供设计原则，不等于本项目使用了 Protobuf 或二进制协议。

## 传输合同

客户端在 HTTP 请求头发送 `X-Survival-Wire: <schema SHA256>`。SHA256 取完整 `business_wire_schema.json` 的 UTF-8、对象 key 排序、无多余空白的规范 JSON。协商是传输元数据，不加入业务请求 JSON，不进入操作指纹、兑换校验、结算 RPC 或幂等键。

仅精确匹配本服务配置的请求可以收到 `{"_bw":[1,"<schema SHA256>",node]}`。无请求头、旧摘要、未知摘要、打包失败或紧凑正文不小于原正文时，服务器返回原始正文。配置新旧并存时各自版本仍可使用旧完整响应，禁止猜测另一版本的数字 ID。客户端必须先解开业务 wire，再处理原来的同响应 profile 引用，最后交给正常业务校验。

| node | 规则 |
| --- | --- |
| 标量 | 保留原 JSON 标量；匹配公开枚举且确实省字节的字符串可用 `[1,id]` |
| 普通对象 | 已知字段 key 优先用字段号的十进制字符串；其余已知配置 ID key 若严格省字节则用 `@` 加数字枚举 ID，覆盖库存等动态 map。未知 key 原样；原 key 若全是数字或以 `~`、`@` 开头，则在前面加一个 `~` 逃逸 |
| 业务数组 | `[0,child,...]`，避免业务数组与协议标签冲突；空数组为 `[0]` |
| 模板对象 | `[2,templateID,{changedFields}]`；只发送与完整模板不同的字段，patch 禁止添加模板之外的 key |
| 已完成同响应引用 | `[3,id]`；每次恢复独立副本，禁止前向、重复定义或循环 |
| 同响应首次定义 | `[4,id,node]`；只在重复子树确有净收益时使用，定义在内部节点完成后登记 |

纯数字字段号必须为有效范围内的标准十进制正整数；未知字段号、非法逃逸、解码后 key 冲突、未知 tag 或重复引用定义均拒绝。JSON 重复 key 不能靠“最后一个获胜”掩盖。原有 Lua JSON 解析器没有保留空对象/空数组的形状；这项既有 Lua 表达限制须单独记录，Python 字节参照测试仍严格区分 `{}` 与 `[]`，不能以此放宽字段语义。

对象及模板 patch 的引用定义／引用解析顺序固定为编码后 key 的 UTF-8 字典序；数组按原顺序。不能依赖 Python 字典插入顺序、JSON 文本字段顺序或 Lua `pairs` 顺序。正常接收端在该顺序下完成定义，才允许后续引用。

`server/player_web_auth/business_wire.pack_bytes(body, advertised_hash)` 只处理成功业务响应；返回 bytes，不抛出可预期的可选优化错误。压缩在事务完成之后执行，不参与资格或发奖判断。任何网络超时、坏 wire、旧回包都不能自动重新发起会扣费或发奖的操作；先按既有回执/只读补档流程恢复。

## 本地表保护与安全边界

schema 仅从本仓库公开字段名、模式名和公开配置 ID 生成；不得含账号、Steam 会话、认证 token、兑换码、支付签名或服务端秘密。固定 ID 表与配置摘要配套，构建时由独立生成器产出本地配置，解密/解析一次后建立索引。读取稳定响应不重新解密或扫描全部配置。

项目现有 Lua `EncryptStrings` 是混淆，不提供密码学保密。新增本地配置若使用密码封装，也不能把随客户端分发的解密材料宣称为不可提取的秘密；其用途是减少明文浏览，真实性依赖发行签名、固定摘要及一致性核验。传输凭据由 HTTPS 和现有认证保护，不放进本地静态表。服务端账本与校验始终权威。

## 预算、复杂度与验收

- 硬限制：输入正文 8 MiB、展开后正文 8 MiB、语义/协议最大深度 64、累计节点 100,000、单响应引用 4096；schema 字段 4096、枚举 16384、模板 512。引用恢复的副本也计入展开节点预算。
- 初始化 O(S) 时间/空间构建字段、枚举、模板索引；S 为本地静态表规模。稳定空闲 O(1)，没有计时器、后台全表扫描、场景遍历或重复跨原生桥调用。
- 每个响应预期时间 O(B + ΣK log K)，空间 O(B+N)；B 为响应字节，N 为节点，K 为单个对象字段数。排序用于与顺序无关的子树身份及可移植的引用次序。模板按对象 key 集合和固定业务 key 索引，单对象只选一个候选，不扫描全部模板。每响应的结构去重以子节点的精确 intern ID 建立 tuple 索引，哈希碰撞由完整 tuple 的精确比较处理，不重复扫描整棵相等子树；标量编码缓存也仅存在于该次响应内。
- 打包后的本地参照解码再比较完整规范 JSON，边界超限或语义不一致则原样退回；这增加一次有界 CPU 遍历，不新增 HTTP、SQL、发奖或原生调用。最终只有真实总字节减少才发送。
- 第一阶段验收门槛：原生业务结果逐值等价；普通与高状态账号都采样；字段省略/清零、VIP 有→无、额度变化、兑换、抽奖重放、无尽批次、配置失配、畸形回包均有检查。相对当前未压缩正文目标减少至少 70%，日常结算优先争取 2 KiB 内、普通写回争取 4 KiB 内，完整长账号以实测为准；这些是工程目标，不是已通过的性能结论。
- 报告分别列原正文、紧凑正文、HTTP 头/TLS 预算、CPU 编解码时间、网络请求数与 SQL 次数。gzip 或更换二进制编码另行测试客户端原生支持；本规则不把离线 gzip 结果当成实际公网费用或 FPS。

校验入口：`python -B tools/generate_business_wire_catalog.py --check`；`--canonical` 只输出规范 JSON；`--update` 显式追加公开配置。临时测试和字节报告统一放树外，不加入游戏包。部署与游廊发布仍执行项目既有不可变来源、签名、回执、完整下载及待发清单规则。

生成器还逐项比较 HEAD 已提交 registry 的完整前缀，包含模板的原始默认值与 JSON 类型；手工重排、删除、替换已有 ID 或把 false 改成 0 均拒绝。首版 HEAD 尚无 schema 时明确报告 `FIRST_VERSION_NO_COMMITTED_SCHEMA`，不能把“没有基线”报告成已验证历史前缀。
