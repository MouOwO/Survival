## 按需扩容建议

- 优先对照更多CPU的同代16 vCPU/32 GiB按量规格，并匹配服务进程/并发配置；32GiB是该档配套容量，不代表本次是缺内存。换硬件后仍须同业务4000人一小时与完整退出/SQL核验，不能承诺自动消除错误。
- 当前数据库容器CPU上限4核。若只升ECS而不审查容器及服务并发限制，新增CPU不会全部自动成为数据库容量；对照要同时记录这些固定限制。
- 单机变配适合提前安排，普通按量ECS变配需重启，不应等玩家已经登录失败才操作。价格以控制台兼容规格及实际订单为准，之前不同代/不同系列报价不能直接当同等CPU能力。
- 若希望高峰无停机增减机器，先建设统一入口、健康检查、会话共享、共享数据库和安全缩容排空。当前认证SQLite/进程内状态不能直接各复制一份就假定一致；数据库成为共同瓶颈时多加API机器也不会线性增容。
- 扩容触发应结合延迟、队列、失败率和CPU，人数只是辅助。必须留出启动/预热时间，不把已恶化的约3000人数当可长期运行的安全线。
- 前期较高人数、一个月后约1000峰值是用户预测；常驻规格按实际1000人长测选，繁忙期额外资源按量。暂不改生产、不新购服务器、不变更计费或删除测试证据。
- 可用预算为每月3000元以内，但需同时覆盖计算、盘、快照、带宽/流量；无法仅凭ECS月租保证总账单。
