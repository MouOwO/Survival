# 2026-11-16 隔离压测：持久化限流额度预留候选

仅本地候选；正式后台、支付、网页登录和游廊均未部署。本候选基于 `20690c11d8b39f4f2f33d2b95664aa61bc9bba26`，在独立树外工作区验证。

## 原因及范围

2000人业务样本中，前端的全局限流、账号限流和会话读取共用SQLite连接锁。保持WAL/FULL时，每次请求两次计数事务会累积等待。数据库加配额2核2GB→4核4GB短测仍有2173/120051已完成HTTP错误、255在线会话残留，不能当成解决方案；不同测试时长不构成严格性能因果对照。

新增显式 `--frontend-rate hot-wal-reserved-v1`，默认仍为baseline；旧hot-rate-v1、hot-wal-full-v1的运行字节保持原有绑定。只接受已复核的索引版、观测版Service和私有SQLite3.51.3链，严格回放源补丁并校验摘要。

## 额度安全与代价

全局计数每次最多预留64个、proxy账号最多4个，先在SQLite事务内持久化增加计数、成功提交后才能使用。限流额度是保守预留量，不再保证等于真实尝试次数。重启、驱逐、策略变化会浪费未用额度，可能提前拒绝；不会返还或制造额度。多个连接/进程以BEGIN IMMEDIATE原子预留，不自动重试SQLite错误。

最多4096个哈希键，索引查找与单项驱逐O(1)，无定时器或全账号扫描。初始化/空闲O(1)，命中0SQL；预留需要固定数目的索引SQL与一次提交。新分钟按需更新键并沿用每分钟一次的旧限流表清理；时钟回退保守拒绝。只优化global-http/proxy，其他scope保留逐次计数。

会话身份、撤销、过期、账号/局绑定仍每次读取并验证。业务RPC、授权检查、奖励outbox、提交、退款、幂等逻辑及写请求重放策略全部沿用父版。没有改成synchronous=NORMAL/OFF或缓存鉴权。

## 已验证及边界

13项组件边界回归覆盖并发、提交失败、重启、驱逐、额度尾数、策略降低和时钟回退；13项真实Service与源链集成覆盖逐次鉴权、撤销/过期、禁止失败转发、WAL/FULL和旧源绑定。集成测试需显式提供SURVIVAL_RESERVATION_PARENT，指向独立prepare生成的不可变观测/WAL源；无夹具时明确跳过。

旧上海隔离机原生Python3.12.3、SQLite3.51.3、WAL/FULL，ABBA组件对照每档500合成账号、4轮、4000次判断：原版4000次提交、约8.44–8.48秒；候选532次提交、约1.174–1.176秒。仅代表限流计数组件；不代表HTTP吞吐、2000人容量或生产验收。首次更大组件超过85秒预算安全停止，原记录保留。

原始证据在 `D:/Survival_本地工具/runs/capacity_parallel_wire_20261116_01/rate_component_probe_01` 和 `rate_component_probe_02`。接下来先原生2账号业务/SQL核对，再单独2000人30分钟；可靠性未通过时不能宣称容量通过或直接上线。最优候选仍需2000人2小时共同活跃长测。

## 并发跨分钟边界修正

独立候选从db425ec继续审查发现：原版在获取Service锁前读取bucket，等待锁期间跨过分钟边界时，额度组件可能把旧时间戳视作时钟回退而误拒绝。候选改为在同一锁内再读一次时钟，然后做清理和预留；真实时钟回退仍保守拒绝。初始化/空闲不变，稳定路径增加一次O(1)时钟读取，无额外SQL/HTTP、定时器或集合扫描。

确定性负对照先在父版失败，修正后通过；15项Service/源链集成和13项额度组件检查均通过。db425ec的两份等待队列在尚无任何业务子进程时取消并记录，旧包与控制保留，不把它作为后续执行源。修正后的冻结提交须重新prepare并绑定原生验证与30分钟对照。
