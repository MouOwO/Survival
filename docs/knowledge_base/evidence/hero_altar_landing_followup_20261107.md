# 英雄祭坛召唤落点与移动状态修复

2026-11-07。本轮仅本地源码更新，后台未变、SDK 上传 0。正式游廊仍为 `2026110104`，Steam manifest `7025356658517360342`。当前离线 Tools 客户端仍运行，不覆盖安装、不重载玩家正在使用的 Lua 状态，不把自动编译缓存作为发行产物。

## 已确认与未确认的原因

- 用户报告召唤英雄卡在祭坛。实际日志是 `hero_shadow_fiend` 的正式英雄实体 994；隔离占位实体为 601，没有选错占位英雄的证据。
- 建筑系统仅对城墙/主城保留阻挡半径，祭坛正常的 `survival_hull_radius` 为 0。旧落点检查忽略半径为 0 的实体，又没有读取已登记的建筑占格，因此能选到祭坛内部。使用真实网格事件与真实落点服务已复现，旧代码在新增断言失败，新代码通过。
- 日志中的 `move_capability=-1` 是缺少查询接口时的回退值，不能视作实际禁止移动。21 次 D 技能被 quickcast 条件校验拒绝，不能用它证明普通右键移动被拒。旧日志缺少坐标、ROOT/STUN 等信息，尚不能证明此次实机卡住完全由占格问题引起。
- 另有失败重试缺口：召唤落点失败后，新英雄会被重新隔离为永久 ROOT、MOVE_NONE 的占位实体；后续若复用该实体，旧代码没有恢复自身隔离状态。此为补充防御修复，本局 601→994 不构成该路径的证据。

## 修复范围

1. `scripts/vscripts/systems/hero_summon_destination.lua` 复用 `grid_placement_system.is_position_occupied` 索引，用英雄圆与附近占格矩形的精确相交检测避开祭坛/研究所等建筑。涵盖角落、负坐标、相切边界；拆除后读取当前占格，无另建缓存。原地形、主城归属、动态单位和隐藏城墙检查保留。
2. `scripts/vscripts/systems/hero_summon_system.lua` 在原生替换、配置实际英雄后重新选择安全落点，避免预检默认半径与真实半径不同，或替换回调改变占用。失败重新隔离，不发布成功、解锁商店或选择无效英雄。不调用无界 `FindClearSpaceForUnit`。
3. 仅在召唤初始化时移除项目自己的 `modifier_survival_placeholder_anchor`，清理占位标记并恢复地面移动；其他战斗 ROOT/STUN 不清除。原有败北/断线隔离继续生效。
4. 每次原生替换输出一条 `HeroSummonLanding`，记录最终落点、尝试数及拒绝原因，便于下局核对；无定时日志。

## 成本与验证

设 B 为建筑列表规模， U 为一次原生半径查询返回的附近单位数， C 为候选数（最多112）， G 为相交网格候选数。原服务已有 O(B + C×U) 的事件触发成本；新服务为 O(B + C×(U+G))。正常半径32/格64的 G≤9，允许的最大半径256时 G≤100；异常半径提前拒绝。空间仍为 O(U)，复用现有建筑网格索引。无初始化全场扫描、无新增定时器/稳定刷新/网络请求。

成功召唤从一次落点解析改为预检和真实英雄复核两次，因此原生 `FindUnitsInRadius` 与原有建筑列表请求均从1次变为2次；回城每次仍为1次解析。不能把完整调用链写成 O(1)。测试普通首个落点4次网格查询，祭坛占用后2次尝试共5次查询，最大支持半径观察66次；这些是受控计数，不是 FPS 或原生耗时测量。

- `test_hero_summon_destination.lua`：保留原地形/岛屿/归属用例，增加真实 `GRID_OCCUPY_REQUEST/GRID_RELEASE_REQUEST`、零半径祭坛、八方向采样遗漏角落、相切/负坐标、实际半径64、异常半径和索引错误拒绝。
- `test_hero_summon_flow.lua`：23场景，包括最终落点改变、最终不可落地、同实体失败重试、继承自身占位状态、保留其他 ROOT、原生清理失败隔离。
