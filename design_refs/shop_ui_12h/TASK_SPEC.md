# UI持续迭代任务：12小时工作预算

## 目标与工作方式

在当前Dota 2游廊项目中，以商城为优先任务，持续优化真实UI组件及其组装效果，使其贴近提供的视觉参考。采用「观察截图→列出偏差→提出候选→实现→重新截图→比较→保留更好的版本」循环。12小时是本次最多投入的工作预算，不是平台持续运行保证；不要靠空等、重复改动或反复改同一个参数凑时间。任务需要实际产物，不是只写分析或计划。

开始后自主推进常规、可逆的视觉修改，不需要每轮等待我回复“继续”。遵守项目已有权限与规则；涉及缺失输入或超出任务范围的操作时明确记录。遇到阻塞先记录原因，继续其他独立任务；全部完成后统一汇报，不为了凑时长重复改动。单纯耗尽时间不等于任务完成。

## 参考优先级

1. 本文件的明确需求、现有商品真实数据、项目已经确认的布局约束。
2. references/01_style_anchor.png：整体气质、云海/青玉/象牙材质、留白、边框精细度、物品与背景的融合；其中英雄、价格与文字是示意内容，不应照搬到真实商品。
3. references/02_assembly_normal.png、03_assembly_hover.png与layout.json：已实现的第8轮基线、组件尺寸和四列布局。第8轮仍可优化，不是质量上限。
4. references/04_cards_comparison.png、05_junction_comparison.png：比较历史，不是要求把每个版本同时组合。
5. references/06_component_board.png：组件索引；棋盘格只表示透明区，不能进入游戏素材。

视觉参考与当前商品类别不同，不能把换成同一张立绘、复制示意数字当成复刻成功。尺寸按布局合同，材质按视觉参考。

## 不改变的内容

- 本轮以UI层面为主，不改战斗、存档、掉落、商品定价、实际奖励和支付接口。
- 原有商城入口、商品数据与点击购买流程继续复用。效果描述是商品上的动态text，不另做商品详情页。
- 付款相关仍使用现有占位展示，不接真实付款、不造真实订单；本次不是支付开发任务。
- 主界面底部HUD、技能范围与属性布局保持已确认状态。
- 保持极简。商品保留Dota 2物品的识别特征，避免页游式巨大金框、爆闪、满屏装饰。
- 关闭按钮是右上角独立叉号，不加方框底；导航选中保留独立光晕与底部对齐金线。
- 文本、名称、价格、货币图标、进度数据必须独立绑定，不能烘焙进卡片图片。
- 示意8件物品不是游戏完整商品表，不能用示意图覆盖所有商品真实资源。
- 同类窗口、导航、按钮、卡片尽量共用尺寸、素材和样式变量，不给每个页面重新做一套。

## 先做项目基线

检查项目说明和UI目录，定位商城XML/CSS/JS及其资源引用；记录当前工作区已有改动，保留原状态。不要覆盖用户未提交的工作。若适合，用独立分支或工作副本保存此次迭代。

检查能否获取实际游戏截图、能否打开与重载商城、能否渲染hover。若不能，以参考包组件预览或项目可运行的替代预览继续独立视觉工作；明确标记“预览验证”，不能声称完成游戏内验证。不要让全部任务因游戏无法启动而停住。

先保存默认、单个商品悬停、左侧选中三种基线截图，以及顶部接缝、侧栏接缝、单张商品局部。截图应同分辨率、同状态、同商品，不用随机画面比较。

## 时间分配建议

| 工作预算 | 任务 | 必须留下的证据 |
|---|---|---|
| 0–1小时 | 资源/组件盘点、实际入口、基线截图、问题排序 | 基线、路径表、Plan.md |
| 1–3小时 | 窗口、标题底图、侧栏衔接、选中光晕、内边距 | 至少2个有区别的衔接候选及局部对比 |
| 3–6小时 | 商品底板、物品大小与投影、名称/价格区、配套材质 | 普通/悬停对比；窄长、宽大、圆形物品适配 |
| 6–8小时 | 描述、购买按钮、hover边缘与动效稳定性 | 状态图、操作检查；可运行时提供录屏 |
| 8–10小时 | 接到真实商城类别：装备、皮肤、抽奖券、礼包 | 已有类别截图；礼包2×2四单元布局 |
| 10–12小时 | 分辨率、长文本、公共组件回归、整理最佳版 | 最佳版、前后对比、资源与接入说明 |

以上是分配建议，不以等时长代替完成度。后续页面仅按项目现有内容与已确认参考处理；无参考或无入口的页面记录缺口，不自行重设计成新风格。

## 每轮迭代协议

计划做16–24个有明确差异的候选实验，可根据证据调整数量；不得为了数量重复保存几乎相同的图片。候选可以是一个组件或一组局部参数，不要求每轮重做整个商城。

1. 查看实际截图，写明位置、偏差、原因假设、准备修改的1–3个变量；至少指出一处仍需提升的细节，或用证据解释该区域已足够接近目标。
2. 优先选择影响最大的偏差，不不断添加装饰。每组关键问题尽量尝试至少2种方案，例如接缝雾化强弱、阴影轻重、展示底深浅。
3. 从当前最佳版生成候选，明确版本号；比较基线/当前最佳/候选，不能把最新候选自动当成最好。
4. 改真实组件，再按原窗口尺寸重新组装截图。不能用单张AI效果图作为已完成实现的证据。
5. 查看全图与100%局部，检查alpha、尖角、发光裁切、字体、点击区域和hover。
6. 把选择依据写入Decisions.md：改善了什么、是否引入代价、保留或淘汰及其原因。未改善则回退候选，而不是层层叠加补丁。
7. 更新Progress.md，写出当前最佳版本、已做检查、下一项实验和阻塞。每完成一组有实质差异的候选保存可恢复检查点。

## 比较标准

下列权重只用于辅助记录主观视觉判断，不能作为“自动验收通过”的证明。评分须对应具体截图位置和可观察变化；无法查看截图时不打视觉分。

| 比较项 | 权重 | 判断依据 |
|---|---|---|
| 参考风格一致性 | 25 | 配色、材质、边框克制程度与目标一致 |
| 衔接与整体连贯性 | 20 | 顶部/侧栏/展示区/名称价格区没有生硬色块与不必要断层 |
| 商品质感与辨识度 | 20 | 物品比例、受光、投影、轮廓清晰；仍能识别真实物品 |
| 文本与信息层次 | 15 | 名称、价格、效果描述清晰，文字没有挤压或烘焙 |
| 交互状态 | 10 | hover、选中、购买按钮清晰；无跳动、遮挡或粘连 |
| 复用与实际实现 | 10 | 使用共用组件；真实组装与预览一致 |

整体评分改善但出现文字裁切、按钮不可点、商品变形等回归时，候选不得成为最佳版。连续3个候选无收益时，冻结该区域并转到下一个独立问题；所有区域稳定后停止实质修改，整理证据和剩余主观不确定性。

## 精确验收

- 基准画布1920×1080，窗口1600×920，位置(160,80)。商城装备卡片296×348，四列两行，横向步长312、纵向366；其余坐标见layout.json。以这份合同为基线，不能每张素材独立适配比例。
- 在基准预览中，共用边缘/网格对齐偏差目标不超过2设计像素；明确必要的布局调整要记录，不偷偷改变既定卡片尺寸。
- 物品图保持源宽高比，不能横向/纵向分别拉伸；原PNG透明区域无残余底色或棋盘格。
- 商品默认/hover、导航默认/hover/选中、购买按钮默认/hover/按下状态可重复显示；描述与购买按钮按既定hover逻辑显示。
- 价格信息底不是按钮。纯装饰层禁止拦截输入。选中导航底线仍在行底端，光晕不能被行边界截断。
- 1280×720、1920×1080、2560×1440、2560×1080检查窗口边界、长名称、长价格、描述与类别切换；不得只靠一张全图截图宣布适配完成。
- 复用同一套卡片壳测试装备、皮肤、抽奖券；礼包按已确认2×2四单元，物品数量变化不挤压价格和购买区。
- 浏览器预览与Panorama不是同一引擎；阴影已有独立PNG，可直接分层组装。不能盲目复制浏览器filter/backdrop-filter等属性。转换项目实现时使用该项目已支持的属性与资源方式，实际游戏截图作为接入验收依据。
- 不使用整张商城截图代替动态窗口；不编造看过游戏截图、录屏、通过编译或运行的结果。

## 最终交付

交付当前最佳版本，而非最后一次实验。提供默认/悬停全图、关键局部、基线与最终对比；提供可复用PNG、源文件、尺寸/锚点/层级表、资源引用表和修改文件列表；给出实际可运行的验证步骤。

保留Plan.md、Progress.md、Decisions.md；简述尝试过的方向、淘汰原因、已验证项和尚未在游戏验证项。若会话/额度/时间中断，先保存当前最佳版本、下一步命令、阻塞与恢复说明，不把中断报告写成最终完成。

开始时直接读取参考图、检查项目并落实第一轮，不停在“我可以帮你”或计划说明上。
